# 3과목 총정리 (이름 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴 (본보기)
- 원인: 데이터 문제입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없습니다. 시스템은 사용자 파일에 없는 사람의 요청을 모두 「등록되지 않은 사용자」로 거부합니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: 새로 넣습니다. hana 를 `"hana": {"role": "sales", "employed": true}` 로 `users.json` 에 적습니다. `role` 은 hana 가 맡을 일에 맞는 역할로 정합니다.
- 고친 뒤 확인: hana 의 요청을 다시 판정해서 「등록되지 않은 사용자」가 사라지는지 봅니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)
- 원인: 데이터가 정리되지 않았습니다. dami 는 퇴사했는데 dami 의 항목이 `users.json` 에 그대로 남아 있어서 같은 시도가 계속 들어옵니다. `employed` 가 `false` 이면 요청은 거부되지만, 남은 항목 때문에 퇴사자 계정 점검에는 계속 걸립니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, dami 의 항목 전체를 `users.json` 에서 지웁니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 무엇일까요?

## 상황 3 · 다른 팀 업무를 잠시 지원함
- 원인: 사람의 업무 때문에 일시적으로 필요한 권한입니다. seoyeon의 sales 역할에는 정산 조회 권한(SETTLE:QUERY)이 없지만, 이번 달 정산 대조를 잠시 지원해야 합니다.
- 고칠 파일: config/exceptions.json
- 어떻게 고치나요: 새로 넣습니다. 예외 항목에 사용자, 권한, 만료 시각, 사유를 기록합니다. 예를 들어 {"id": 6, "user": "seoyeon", "permission": "SETTLE:QUERY", "expires": "2026-11-05 18:00", "reason": "월말 정산 대조 지원"}처럼 추가합니다. 잠깐 필요한 권한이므로 users.json의 역할은 바꾸지 않습니다.
- 고친 뒤 확인: 만료 전에는 「예외 6번」으로 허용되고, 만료 시각 이후에는 「권한 없음」으로 거부되는지 확인합니다.
- 더 써 보고 싶은 것(선택): 잠깐 필요한 권한은 역할을 바꾸는 대신 예외로 주는 이유는 무엇일까요?

## 상황 4 · 새 권한이 필요함
- 원인: 권한 요청·검토·승인·부여 절차가 필요한 상황입니다. junho가 영업 실적 정정에 필요한 SALES:CHANGE를 요청했지만, 절차가 없으면 담당자가 설정 파일을 직접 수정하게 되어 승인자와 승인 이력이 남지 않습니다.
- 고칠 파일: 새로 만드는 req_create.py, req_review.py, req_grant.py
- 어떻게 고치나요:create_request로 요청서를 만들고, 요청자 본인이 아닌 검토자가 approve_request로 승인한 뒤, 승인된 요청서만 grant_request로 부여합니다. 부여할 때 예외 목록에 권한과 만료 시각 등을 추가합니다.
- 고친 뒤 확인: 요청서 상태가 reviewing → approved → granted로 바뀌고, junho의 SALES:CHANGE 요청이 예외로 허용되는지 확인합니다. 이미 처리된 요청이나 본인 요청을 본인이 승인하려는 경우에는 승인되지 않아야 합니다.
- 더 써 보고 싶은 것(선택):요청자가 자기 요청을 직접 승인하지 못하게 막는 이유는 무엇일까요?

## 상황 5 · 안 쓰는 권한이 쌓임
- 원인:사용 이력이 오래된 권한이나 사용 기록이 없는 권한이 계속 남아 있기 때문입니다. 마지막 사용 후 90일이 지난 권한은 회수 후보가 됩니다. 다만 오래 쓰지 않았더라도 결산 때처럼 드물게 필요한 권한이 있고, 퇴사자의 권한은 제외 목록에 있어도 회수 대상입니다.
- 고칠 파일:점검은 review_unused.py, 사용 이력은 config/access_log.json, 회수 제외 사유는 config/exclude_list.json입니다.
- 어떻게 고치나요:
    - 케이스 A: junho의 SALES:QUERY처럼 91일 동안 사용하지 않은 권한은 회수 후보로 분류합니다. 90일을 초과해야 하므로 정확히 90일인 권한은 후보가 아닙니다.
    - 케이스 B: seoyeon의 SALES:CHANGE처럼 결산 때만 쓰는 권한은 exclude_list.json에 사용자·권한·제외 이유를 추가해 회수 후보에서 제외합니다.
    - 케이스 C: 사용 이력이 없는 gaeun의 ACCOUNT:CHANGE처럼 사고 대응에만 쓰는 권한도 필요한 이유를 확인하고 제외 목록에 사유와 함께 추가합니다.
    - 케이스 D: 제외 목록에 있더라도 퇴사자 dami의 권한은 회수 대상입니다. 필요하면 dami의 제외 항목도 정리합니다.
- 고친 뒤 확인:점검을 다시 실행해 90일 초과 권한은 회수 후보에, 정당한 사유가 등록된 권한은 회수 제외에, 퇴사자의 권한은 회수 대상에 분류되는지 확인합니다.
- 더 써 보고 싶은 것(선택):사용 기록이 없다는 이유만으로 권한을 바로 회수하면 안 되는 경우는 무엇일까요?

## 상황 6 · 민감한 권한을 회수해야 함
- 원인:권한의 민감도와 회수 영향에 따라 승인 절차가 필요한 상황입니다. 예외 권한 삭제처럼 영향이 작고 읽기 권한인 경우와, 퇴사자의 역할 전체를 비우거나 쓰기 권한을 회수하는 경우는 영향이 다릅니다.
- 고칠 파일:실제 회수 대상에 따라 config/exceptions.json, config/users.json, config/roles.json을 사용하며, 승인 판단은 revoke_approve.py, 회수 결과 이력은 revocation_log.json에 남깁니다.
- 어떻게 고치나요:
    - 케이스 A: seoyeon의 정산 조회 예외(예외 1번)는 exceptions.json에서 해당 항목을 삭제합니다. 영향 권한이 1개인 읽기 권한이므로 승인 없이 실행할 수 있습니다.
    - 케이스 B: 퇴사자 dami의 sales 역할을 비우는 경우에는 users.json에서 역할을 해제합니다. 역할 권한 2개에 영향을 주므로 보안 책임자의 승인을 먼저 받습니다.
    - 케이스 C: junho의 SALES:CHANGE처럼 민감한 쓰기 권한은 승인이 없으면 실행하지 않고 대기 상태로 둡니다.
    - 케이스 D: roles.json에서 finance 역할의 SALES:QUERY를 빼면 그 역할을 가진 모든 사용자에게 적용되므로, 영향을 받는 사용자 수를 먼저 확인합니다.
    - 케이스 E: 승인이 거절되거나 결정되지 않았다면 회수하지 않습니다. 거절 이유를 해결한 뒤 새로 승인을 받아야 합니다.
- 고친 뒤 확인: 회수 계획별로 승인 필요 여부와 실행·대기 결과를 확인하고, revocation_log.json에 이력이 저장되는지 봅니다. 승인 대기 건은 권한이 그대로 유지되어야 합니다.
- 더 써 보고 싶은 것(선택):권한을 회수할 때 영향받는 사용자와 권한 수를 미리 계산하는 이유는 무엇일까요?

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨
- 원인: 접속 시간·위치 조건이 빠졌거나 실제 업무 방식과 맞지 않는 규칙 문제입니다. 조건이 없는 권한은 새벽이나 외부에서도 허용될 수 있고, 반대로 정상 직원의 VPN 접속이 허용 목록에 없으면 업무 중에도 거부될 수 있습니다.
- 고칠 파일:config/conditions.json
- 어떻게 고치나요:
    - 케이스 A: SALES:CHANGE 조건이 빠져 있다면 허용 업무 시간과 접속 위치를 추가합니다. 예를 들어 업무 시간은 9시부터 18시 전까지, 접속 위치는 office, vpn으로 지정합니다.
    - 케이스 B: gaeun의 ACCOUNT:CHANGE가 VPN에서 거부된다면 먼저 실제 재택·외근 업무인지 확인합니다. 업무상 VPN이 필요하고 보안상 허용할 수 있다면 해당 권한의 networks에 vpn을 추가합니다. 업무상 필요가 확인되지 않으면 규칙을 그대로 둡니다.
- 고친 뒤 확인:조건을 추가하거나 수정한 뒤 같은 요청을 다시 판정합니다. 허용 시간·접속 위치에서는 허용되고, 조건을 벗어난 새벽 또는 외부 접속은 거부되는지 확인합니다.
- 더 써 보고 싶은 것(선택):정상 직원의 불편을 줄이려고 접속 규칙을 완화하기 전에 어떤 사실을 확인해야 할까요?

## 상황 8 · 매주 어긋남을 확인해야 함
- 원인:점검과 로그 집계를 사람이 수작업으로 처리하거나, 경고 기준이 현실과 맞지 않거나, 로그 데이터가 제대로 모이지 않는 문제입니다. 수작업은 시간이 오래 걸리고 매주 같은 기준으로 확인했는지 비교하기 어렵습니다.
- 고칠 파일:새로 만드는 checklist.py, log_summary.py, weekly_report.py; 경고 기준은 config/alert.json; 로그 원본은 server_log.jsonl입니다.
- 어떻게 고치나요:
    - 케이스 A: 점검 세 가지(퇴사자 계정, 만료 예외, 부서·역할 불일치), 로그 집계, 주간 보고서 생성을 코드로 만듭니다.
    - 케이스 B: 거부율 경고 기준이 맞지 않으면 alert.json의 deny_rate_limit 값을 조정하고 변경 이유를 기록합니다. 예를 들어 거부율 40%는 기준 30%에서는 경고지만 기준 50%에서는 경고가 아닙니다. 기준을 바꿨다고 실제 거부 요청이 줄어든 것은 아닙니다.
    - 케이스 C: 로그가 비어 있다면 거부율 0%를 안전하다는 뜻으로 해석하지 않습니다. 먼저 서버가 요청을 기록했는지, 로그 파일 경로와 수집 상태가 정상인지 확인합니다. 자료에 구체적인 수정 파일·코드는 제시되어 있지 않으므로 원인을 확인한 뒤 조치해야 합니다.
- 고친 뒤 확인:주간 보고서에 요청 현황, 거부 사유, 점검 결과, 조치가 필요한 항목이 정리되는지 확인합니다. 같은 로그를 기준으로 집계 결과가 일관되게 나오고, 경고 여부가 설정한 기준과 일치하는지 봅니다.
- 더 써 보고 싶은 것(선택):로그가 한 건도 없을 때 거부율 0%만 보고 안전하다고 판단하면 안 되는 이유는 무엇일까요?
