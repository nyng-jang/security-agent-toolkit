## 5교시 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

### 문제 5-1 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 연결된 사건의 사용자와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 연결된 사건의 사용자 ③ 이유
  - 답: 연결된 사건의 사용자는 **gaeun** 한 명이고, 이유는 「서로 다른 로그 3종류 · 41분 안」입니다(web · server · saas 세 로그의 이벤트가 09:33 ~ 10:14 사이 41분 안에 모여 있음).

```
--- 단계 1: IP 로 사용자를 알 수 있는 웹 실패 이벤트 1 개
--- 단계 2: 사용자별로 시간순으로 놓은 이벤트 24 개
gaeun 의 이벤트 (시각 · 로그 · 행동 · 결과)
2026-11-02 09:33:51 web GET /admin 실패
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
--- 단계 3: 60 분 안에 서로 다른 로그로 연결된 사건
{'user': 'gaeun', 'reason': '서로 다른 로그 3종류 · 41분 안'}
--- 단계 4: 로그 종류는 여럿이지만 시간 차가 60분을 초과해 연결되지 않은 사용자
{'user': 'seoyeon', 'source_count': 2, 'span_minutes': 555}
```

- (나) 🔍 단계 2에 나온 gaeun 의 이벤트 5개는 어느 로그(`source`)에서 왔고, 왜 한 사건으로 연결됐나요? 이 사건만으로 공격이라고 확정할 수 있는지도 적어 주세요.
  - 쓸 내용: ① gaeun 이벤트 5개의 로그(source) ② 연결된 까닭 ③ 공격이라고 확정할 수 있는지와 그 근거(단계 2 의 action · result 와 오전 2교시 판정 이유)
  - 답: gaeun 의 이벤트 5개는 웹(`web`) 1개(09:33 `GET /admin` 실패) · 판정 서버(`server`) 3개(10:05 · 10:09 · 10:14 `ACCOUNT:CHANGE` 실패) · SaaS(`saas`) 1개(10:12 `login` 성공)입니다. 서로 다른 로그가 3종류로 조건 ①(2종류 이상)을 만족하고, 첫 이벤트 09:33 부터 마지막 10:14 까지 41분으로 조건 ②(60분 이내)도 만족해서 한 사건으로 연결됐습니다. 하지만 이것만으로 공격이라고 확정할 수는 없습니다. 오전 2교시에서 서버가 거절한 `ACCOUNT:CHANGE` 3건은 3과목 규칙으로 다시 판정하면 「허용」(규칙은 허용인데 서버가 거절)이었고, 웹의 `/admin` 실패는 1건뿐이며, SaaS 로그인은 평소 IP 기록이 없는 상태에서 성공했습니다. 같은 시간대에 여러 로그에서 기록이 확인된다는 것만 알 수 있고, 원인(서버 설정 오류인지, 권한 남용 시도인지)은 이 기록만으로 알 수 없어서 먼저 확인할 사건으로 두는 것입니다.

- (다) 🔍 seoyeon 은 서로 다른 로그에 나오지만 연결되지 않았습니다. 단계 4 의 두 숫자(로그 종류 수와 처음부터 마지막까지의 분)로 두 조건을 비교해 연결되지 않은 이유를 설명하고, 하나의 사건으로 연결하지 않아서 탐지하지 못할 수 있는 것을 오전 3교시 출력에서 seoyeon 이 나온 규칙과 연결해 적어 주세요.
  - 쓸 내용: ① 연결되지 않은 이유(두 조건과 단계 4 의 두 숫자) ② 연결하지 않아서 탐지하지 못할 수 있는 것
  - 답: seoyeon 은 단계 4 에서 로그 종류가 **2**(server · saas)라서 조건 ①(2종류 이상)은 만족하지만, 첫 이벤트부터 마지막 이벤트까지가 **555분**(09:05 SaaS 로그인 ~ 18:20 서버 `SALES:CHANGE` 실패)이라서 조건 ②(60분 이내)를 만족하지 못해 연결되지 않았습니다. 두 조건이 모두 맞아야 연결하므로 하나만 맞는 seoyeon 은 사건이 되지 않습니다. 오전 3교시 출력에서 seoyeon 은 「평소와 다른 IP」(17:38 에 평소 198.51.100.9 가 아닌 203.0.113.80 으로 로그인)와 「대량 다운로드」(17:40 ~ 17:42 에 5번 내려받음) 규칙에 나왔습니다. 하나의 사건으로 연결하지 않으면, 이 SaaS 이상 사용과 서버의 거절(11:40 `SETTLE:QUERY` 권한 없음 · 18:20 `SALES:CHANGE` 실패)이 같은 사용자의 기록이라는 점을 탐지 결과에서 한눈에 확인하기 어렵습니다. 특히 17:38 새 IP 로그인 → 대량 다운로드 → 18:20 서버 거절은 42분 차이로 짧은데, 하루 전체 범위(555분)로 재면 60분 기준에 걸리지 않아 놓칠 수 있습니다.

## 6교시 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

### 문제 6-1 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, high · mid · low 에 각각 어떤 대상이 들어갔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② high 에 들어간 대상 ③ mid 에 들어간 대상 ④ low 에 들어간 대상
  - 답: high 는 **dami**(60), mid 는 **seoyeon**(45) · **gaeun**(40) · **jiwoo**(35), low 는 **198.51.100.90**(30) 입니다.

```
--- 단계 1: 탐지된 규칙 8 건
--- 단계 2: 대상별 점수
entity
dami             60
seoyeon          45
gaeun            40
jiwoo            35
198.51.100.90    30
Name: points, dtype: int64
--- 단계 3: day03_risk_scores.json 에 5 건 저장
--- 단계 4: 등급 · 대상 · 점수 · 이유
high dami 60 ['퇴사한 계정']
mid seoyeon 45 ['평소와 다른 IP', '대량 다운로드']
mid gaeun 40 ['규칙은 허용인데 서버가 거절', '여러 로그 연결']
mid jiwoo 35 ['업무 시간 밖 로그인', '평소와 다른 IP']
low 198.51.100.90 30 ['경로 스캔']
```

- (나) 🔍 seoyeon 의 점수가 어떤 규칙의 점수를 더해 나왔는지 적고, 점수만 저장하지 않고 이유(`reasons`)를 함께 저장하는 까닭을 적어 주세요.
  - 쓸 내용: ① seoyeon 점수를 이룬 규칙과 점수 ② 이유를 함께 저장하는 까닭
  - 답: seoyeon 의 45점은 **평소와 다른 IP 20점 + 대량 다운로드 25점** 을 더한 값입니다. 이유를 함께 저장하는 까닭은 점수 45만으로는 왜 mid 인지, 무엇을 확인해야 하는지 담당자가 알 수 없기 때문입니다. `reasons` 에 「평소와 다른 IP · 대량 다운로드」가 있으면 SaaS 로그인 IP 와 다운로드 기록부터 바로 확인할 수 있고, 등급의 근거를 다른 사람에게 설명할 수 있으며, 나중에 점수 기준(WEIGHTS)을 바꿀 때 어떤 규칙이 등급에 영향을 주는지도 따질 수 있습니다.

- (다) 🔍 198.51.100.90 은 경로 스캔 하나에 해당하지만 low 입니다. low 는 점수 기준상 낮은 등급이라는 뜻입니다. low 인 이유를 점수와 기준으로 설명하고, 이 IP 의 기록을 무시해도 되는지 샘플의 값(그 IP 의 요청 3개의 `result`)으로 판단해 적어 주세요.
  - 쓸 내용: ① low 인 이유(점수와 기준) ② 무시해도 되는지(오전 4교시 find_scan_ips 결과나 normalized_events.json 의 이 IP 요청 시각 · 경로 · 결과를 근거로)
  - 답: 198.51.100.90 은 「경로 스캔」 30점 하나뿐이라 mid 기준 35 에 못 미쳐(30 < 35) low 입니다. IP 대상에는 경로 스캔 규칙 하나만 적용되므로 이 IP 는 30점을 넘을 수 없어 항상 low 가 됩니다. 그래도 무시하면 안 됩니다. normalized_events.json 에서 이 IP 는 09:20:10 `GET /.env`, 09:20:11 `GET /wp-login.php`, 09:20:12 `GET /phpmyadmin` 을 2초 안에 요청했고 3개 모두 `result` 가 `실패` 였습니다. 지금은 모두 실패해서 피해가 없었지만, 사람이 아닌 스캐너가 비밀 키 파일과 관리자 페이지를 찾은 흔적이므로, 같은 IP 가 다시 오거나 요청이 성공하면 바로 확인할 수 있게 기록을 남겨 두어야 합니다. low 는 확인 순서가 뒤라는 뜻이지 안전하다는 뜻이 아닙니다.
