# 2교시: LLM을 API로 호출

## **왜 보안 관제에 LLM이 필요할까?**

- **기존 방식의 한계**: 지금까지 만들었던 '탐지 규칙(Rule)'은 우리가 미리 정해둔 정확한 조건과 매칭되는 로그만 골라냈습니다. 규칙에 없는 새로운 유형의 로그는 그대로 통과해 버리는 허점이 있었죠.
- **LLM의 역할**: LLM은 복잡한 로그 한 줄을 통째로 읽고, 이게 **"무슨 뜻인지 문장으로 친절하게 설명"**해 줄 수 있습니다. 즉, 사람이 보안 모니터링 화면을 보면서 한 줄씩 수동으로 분석하던 일을 인공지능이 대신해 주는 것입니다.

## **LLM을 API로 호출하는 삼총사: 주소 · 헤더 · 본문**

우리가 웹브라우저(ChatGPT, Gemini 등) 창에 대화하듯 쓰는 것을 파이썬 코드로 할 때는 컴퓨터끼리 통신하는 방식을 맞춰야 합니다. 2교시에서는 지난주에 배운 `requests.post()` 도구를 그대로 사용합니다.

- **주소 (URL)**: 인공지능 서비스 서버가 요청을 대기하고 있는 인터넷 주소입니다.
- **헤더 (Headers)**: 인공지능을 사용할 수 있는 권한을 증명하는 **'출입증'**입니다. 아침 과제로 발급받은 비밀 키(`api_key`)를 `Bearer`  뒤에 한 칸 띄우고 붙여서 전송합니다.
- **본문 (Body)**: 인공지능에게 보낼 **'질문 내용'**과 **'쓸 모델 이름'**을 딕셔너리(`{ }`) 형태로 담아 보냅니다. 이때 질문을 던지는 주체를 유저(`"role": "user"`)로 설정합니다.

## **가장 중요한 주의점: 환각 (Hallucination)**

실무 자동화를 할 때 반드시 머릿속에 새겨야 하는 인공지능의 치명적인 한계입니다.

- **LLM은 검색기가 아니다**: 인공지능은 어딘가에서 사실을 '조회'해서 정답을 찾는 게 아닙니다. 그저 통계적으로 **"다음에 올 확률이 높은 그럴듯한 단어들을 이어 붙여서"** 문장을 만들어 낼 뿐입니다.
- **아는 척 거짓말을 한다**: "특정 IP 주소가 어느 통신사 꺼냐?"라고 LLM에게 물어보면, 실제 조회 결과(삼성SDS)와 다르게 'SK텔레콤', 'LG유플러스' 등 매번 틀린 답을 진짜인 것처럼 당당하게 지어냅니다. 문장이 너무 자연스러워서 사람이 속기 쉽습니다.
- **올바른 협업 프로세스**:
    - ❌ **나쁜 예**: LLM에게 실제 데이터 조회나 사실 판단을 통째로 맡기기
    - ⭕ **바른 예**: 팩트 체크(통신사, 위치 등)는 실제 데이터 등록 정보를 조회하는 **조회 API**로 명확하게 처리하고, **LLM에게는 복잡한 내용 요약이나 문장 설명만 맡기기**. 최종 판단은 항상 사람이 합니다.

# **3교시: 프롬프트로 답의 모양을 정한다**

**💡 3교시가 왜 필요한가요?**

그냥 로그 한 줄만 LLM(Gemini)에게 툭 던지면, 자기 마음대로 영어로 아주 길게 조목조목 설명하느라 **토큰(돈)을 엄청나게 많이 써요.** 💸또한, 매번 답하는 스타일(길이, 단어)이 달라지면 뒤쪽 파이썬 코드가 그 답을 받아서 자동으로 처리할 수가 없게 됩니다. 그래서 **"내가 원하는 양식으로만 딱 대답해!"**라고 제약을 걸어두는 기술이 필요합니다.

---

## **역할 분담하기 (`system`과 `user`)**

LLM에게 요청을 보낼 때 `messages`라는 리스트 안에 두 가지 역할을 나누어 담아야 해요.

- **`system` (시스템):** LLM에게 역할을 부여하거나 반드시 지켜야 할 절대적인 규칙을 정해줍니다.
    - *예시:* `"당신은 보안관제 애널리스트입니다. 한 문장으로만 답합니다."`
- **`user` (유저):** 우리가 실제로 물어볼 질문이나 분석할 로그 데이터 자체를 넣습니다.
    - *예시:* `"로그: 2026-10-06 01:48:09 WARN failed login..."`

> 🙋‍♂️ **과외쌤의 꿀팁:** 역할을 주면 LLM이 엉뚱한 소리를 안 하고 보안 직무에 맞는 단어와 판단 기준으로 대답의 폭을 확 좁혀서 답변해요!
> 

---

## **답을 파이썬이 다루기 쉬운 `JSON`으로 받기**

단순한 문장으로 받으면 파이썬 코드가 다루기 힘들기 때문에, 딕셔너리 구조와 똑같은 **JSON 형식**으로 출력하라고 지시합니다.

- **지시 예시:** `"다음 로그를 분석해 JSON으로만 답하세요. 키는 severity와 summary 둘입니다."`
- 이렇게 지시하면 LLM이 아래처럼 예쁘게 중괄호를 쳐서 답을 보내줍니다.
    
    **json**
    
    ```
    {"severity":"high","summary":"root 로그인 실패"}
    ```
    
    코드를 사용할 때는 주의가 필요합니다.
    
- 이렇게 받아야 나중에 파이썬에서 `result["severity"]`나 `result["summary"]`로 원하는 값만 쏙쏙 꺼내 쓸 수 있어요.

---

## **예시 보여주기 (`few-shot`)**

LLM에게 "답변을 짧게 해라", "한국어로 해라" 구구절절 설명하는 것보다, **"이런 모양으로 답해라" 하고 본보기를 딱 하나 보여주는 게 훨씬 효과적**이에요. 이걸 인공지능 용어로 **퓨샷(Few-shot)** 기법이라고 부릅니다.

- **프롬프트에 예시 추가하기:**`'예시: {"severity": "high", "summary": "admin 로그인 실패"}'`
- 이렇게 예시를 덧붙여 주면 LLM이 그 **키 이름, 순서, 길이, 언어(한국어)까지 그대로 복사하듯 따라 부릅니다.**

## **AI의 랜덤성 조절하기 (`temperature: 0`)**

LLM은 원래 물어볼 때마다 다른 말을 하는 확률 모델이에요. 하지만 우리 같은 보안 자동화 프로그램에서는 매번 답이 바뀌면 곤란하겠죠?그래서 본문(`body`) 설정에 `"temperature": 0`을 넣어줍니다.

- 숫자가 0에 가까울수록 가장 확률이 높은 **일관된 답변**을 내놓게 됩니다.
- **주의할 점:** `temperature`를 0으로 낮추어도 완벽히 똑같은 답이 안 나올 때가 있고, **환각(거짓말) 현상이 완전히 사라지지는 않아요!** 따라서 최종 판단은 언제나 사람이 하거나 실제 조회 API를 교차 검증해야 합니다.

---

```python
# 1. 프롬프트 조각들을 공백(" ")을 두고 이어 붙여서 user 질문을 만듭니다.
question = instruction + " " + example + " 로그: " + log

# 2. system(역할)과 user(질문)를 리스트로 묶습니다.
messages = [
    {"role": "system", "content": "당신은 보안관제 애널리스트입니다."},
    {"role": "user", "content": question}
]

# 3. 모델 이름, 일관성을 위한 temperature 0, 그리고 messages를 담아 본문을 만듭니다.
body = {
    "model": "gemini-3.5-flash-lite",
    "temperature": 0,
    "messages": messages
}

```

### 3-4 문제 오답

```python
# ── 미리 채워 둔 줄입니다. 고치지 않습니다 ──
log = "2026-10-06 01:48:09 WARN failed login for root from 198.51.100.23"
instruction = "다음 로그를 분석해 JSON 으로만 답하세요. 키는 severity 와 summary 둘입니다. severity 는 high, medium, low 중 하나입니다."
example = '예시: {"severity": "high", "summary": "admin 로그인 실패"}'
# ── 여기까지 ──

# 1. question 이라는 변수를 만들어 instruction, example, "로그: " + log 를 공백 한 칸씩 두고 이어 붙이세요
question = instruction, example, "로그: " + log

# 2. messages 라는 변수를 만들어 system 딕셔너리와 user 딕셔너리를 담으세요
messages = [
    {"role": "system", "content": question},
    {"role": "user", "content": log}
]

# 요청 본문 — 모델 이름과 messages
body = {"model": "gemini-3.5-flash-lite", "messages": messages}

response = post_to_llm(body)                                  # 키 읽기 · 헤더 · 요청을 함수가 대신 한다 (2.4)

data = response.json()                                        # 응답(JSON 문자열)을 딕셔너리로 바꾼다
answer = data["choices"][0]["message"]["content"]             # 답 문장 꺼내기: choices → 0번 → message → content
print(answer)
```

**1. 문자열을 이어 붙일 때 쉼표(`,`)를 쓰면 튜플(Tuple)이 됩니다.**

- **작성하신 코드:** `question = instruction, example, "로그: " + log`
- **원인:** 파이썬에서 문자열들을 쉼표로 연결하면 글자가 합쳐지는 게 아니라 `('다음 로그...', '예시...', '로그: ...')` 같은 **튜플 자료형**이 되어 버립니다. LLM은 이 형식을 읽지 못합니다.
- **해결책:** 힌트에 적힌 대로 **공백 한 칸(`" "`)을 두고 더하기(`+`) 기호**로 이어 붙여야 합니다.

# 4교시: **JSON 답을 안전하게 읽는다**

3교시에서 LLM에게 "JSON으로만 답해줘"라고 지시하면, LLM은 센스 있게(?) 답변 앞뒤에 마크다운 코드 블록 표시인 ````json`과 `````을 붙여서 보내줍니다.

문제는 이 마크다운 표시들이 포함된 문자열을 파이썬의 `json.loads()`에 그대로 집어넣으면, `{`로 시작하지 않는다는 이유로 **`JSONDecodeError`가 발생하며 프로그램이 통째로 멈춰버립니다.**

만약 로그 100건을 자동 분석하는 중이었다면, 겨우 1건의 에러 때문에 나머지 99건의 분석 결과까지 모두 날아가게 되는 셈이죠. 따라서 이를 안전하게 처리하는 가공 과정이 필요합니다.

---

## **코드 블록 표시 깨끗하게 지우기 (`replace`, `strip`)**

문자열에서 필요 없는 글자를 지울 때는 **더 긴 글자 목록인 ````json`을 먼저 지워야 합니다.** 짧은 `````을 먼저 지워버리면 `json`이라는 글자가 찌꺼기처럼 남아 에러를 유발합니다.

```python
clean = text.replace("```json", "") # 1. 긴 표시 먼저 지우기
clean = clean.replace("```", "")     # 2. 남은 백틱 표시 지우기
clean = clean.strip()                # 3. 앞뒤 공백과 줄바꿈 정리
```

## **예외 처리로 프로그램 생명 연장하기 (`try - except`)**

LLM이 가끔 말을 안 듣고 그냥 생문장(텍스트)으로 답변할 때가 있습니다. 이때 에러가 나더라도 죽지 않고 다음 로그로 넘어가도록 `try-except` 문으로 감싸줍니다. 실패하면 에러 대신 `None`을 돌려주는 것이 안전한 설계 방식입니다.

```python
import json

try:
    result = json.loads(clean) # 정상적인 JSON 모양이면 딕셔너리로 변환 성공!
except json.JSONDecodeError:
    result = None              # 읽지 못하는 문장이면 조용히 None 담기
```

## **사용하기 전에는 무조건 검사하기 (`if result:`)**

`None`이 담긴 변수에 대고 `result["severity"]` 처럼 키값을 꺼내려고 하면 `TypeError`가 납니다. 따라서 **값이 제대로 들어있을 때만 꺼내 쓰도록 `if` 조건문**을 먼저 걸어주어야 합니다.

```python
if result:
    print(result["severity"], "|", result["summary"])
else:
    print("읽지 못했습니다")
```

# 5교시: AI 에이전트와 도구 호출

- 핵심: LLM(AI)에게 직접 일을 시키면 거짓말(환각)을 하거나 파일 접근을 못 하니, AI에게는 어느 도구(함수)를 쓸지 '고르게만' 하고 실제 실행은 우리 컴퓨터(파이썬 코드)가 안전하게 처리하도록 만드는 것
- 오전 수업의 한계: 오전에 만든 LLM은 로그를 '설명'하거나 텍스트를 '요약'하는 일은 잘했습니다. 하지만 "이 계정의 로그인 실패 횟수가 총 몇 번이야?"라고 물으면, 실제 파일 내용을 열어보거나 연산할 수 없기 때문에 그럴싸한 숫자를 지어내는 환각(Hallucination) 현상이 발생합니다.
- 해결책: AI에게 모든 걸 맡기지 않고 일을 나누는 것입니다. 실제 파일 계산은 정확하고 안전한 우리 컴퓨터(파이썬 코드)가 하고, AI에게는 상황에 맞는 기능을 '고르는 역할'만 주는 것입니다.

---

- 🤖 AI 에이전트 (Agent)
    - 단순히 질문에 답만 하는 챗봇과 다릅니다. 목표를 주면 스스로 판단해서 순서를 정하고, 필요한 도구를 골라 쓰면서 임무를 완수하는 주도적인 프로그램을 뜻합니다.
- 🧰 도구 (Tool)
    - AI가 쓸 수 있도록 개발자가 미리 컴퓨터에 만들어 둔 파이썬 함수입니다. (예: `count_failed_logins`, `lookup_ip`)
    - AI가 인자값을 다루기 쉽도록 '딕셔너리 하나(`args`)'만 인자로 받게 만드는 것이 규칙입니다.
- 📞 도구 호출 (Tool Calling / Function Calling)
    - 모델이 목표를 보고 "어떤 함수를 어떤 값으로 부를지" 결정해서 개발자에게 알려주는 구조입니다.
    - 이때 AI가 함수를 직접 실행하는 것이 절대 아닙니다! AI는 단지 `{"tool": "함수이름", "args": {"값"}}`이라는 텍스트(JSON) 제안서만 던질 뿐입니다.
- 📝 도구 목록 (`tools_text`)
    - AI가 고를 수 있도록 우리가 프롬프트에 적어주는 "쓸 수 있는 함수들의 설명서"입니다. AI는 이 목록을 읽고 어떤 도구가 적합할지 판단합니다.

## 에이전트의 전체 작동 흐름

1. **목표 + 도구 목록 전달**: 개발자가 AI에게 "목표: admin 실패 횟수 세줘"라는 말과 함께 "내가 만든 도구 리스트"를 프롬프트로 묶어 보냅니다.
2. **도구 고르기 (AI의 역할)**: AI가 제안서(JSON 문자열)를 보냅니다. (`{"tool": "count_failed_logins", "args": {"user": "admin"}}`)
3. **도구 실행 (파이썬의 역할)**: 우리 파이썬 코드가 AI가 준 제안서를 읽고, 진짜 함수를 실행해서 정확한 결과 데이터(예: 숫자 `4`)를 얻어냅니다. **(보안상 가장 중요한 단계! 우리가 실행 여부를 통제할 수 있습니다.)**
4. **최종 답변 생성 (AI의 역할)**: 도구가 찾아낸 정확한 팩트(`4`)를 AI에게 다시 쥐여주면서 "이 결과로 사람에게 친절하게 한 문장으로 답해줘"라고 시킵니다. AI는 팩트를 기반으로 환각 없이 완벽한 답변 문장을 만들어 냅니다.

| **하려는 일** | **쓰는 코드** |
| --- | --- |
| 도구를 만든다 | `def count_failed_logins(args):` … `return count` |
| LLM 에게 고르게 한다 | `call_llm(tools_text + "목표: " + goal)` |
| 고른 것을 읽는다 | `choice = parse_llm_json(text)` · `choice["tool"]` · `choice["args"]` |
| 위 두 줄을 한 번에 | `choice = choose_tool(goal)` |
| 우리 코드로 실행한다 | `if choice["tool"] == "…":` `result = 도구(choice["args"])` |
| 결과로 답을 만든다 | `call_llm("목표: … 실행한 결과는 … 한 문장으로 답하세요.")` |

# 6교시: 이름으로 함수 찾아 실행하기

> 조건문(**`if-elif`**) 없이, 이름(문자열)만으로 원하는 함수를 찾아 자동으로 실행하는 구조 만들기
> 

5교시에는 LLM이 고른 도구 이름에 맞춰 일일이 `if`, `elif` 문을 써서 함수를 실행했습니다. 하지만 도구가 많아지면 코드가 너무 길어지고 관리가 힘들어집니다. 또한 LLM이 도구 목록에 없는 이름을 지어내서 답하면 코드가 그냥 조용히 넘어가 버려 에러 추적이 안 된다는 치명적인 단점이 있음. → 레지스트리와 라우터로 해결!

- **레지스트리 (Registry)**: 도구의 **이름(문자열)**과 실제 **함수(객체)**를 짝지어 저장해 둔 **딕셔너리**입니다.
- **라우터 (Router)**: 레지스트리를 참고하여, 전달받은 이름에 해당하는 실제 함수를 찾아 **자동으로 실행해 주는 코드(함수)**입니다.

---

## 레지스트리 (Registry)

파이썬에서는 함수의 이름 뒤에 괄호를 붙이지 않으면 ‘함수 실행 결과’가 아니라 ‘함수 자체(객체)’를 가리키게 됨

→ 딕셔너리의 Value로 저장 가능

```python
# 이것이 바로 레지스트리(Registry) 구조입니다.
tool_registry = {
    "lookup_ip": lookup_ip,  # "문자열 이름" : 괄호 없는 실제 함수!
    "count_failed_logins": count_failed_logins
}
```

이렇게 이름과 함수를 짝지어두면 나중에 LLM이 `"lookup_ip"`라는 문자열을 보내왔을 때 `tool_registry.get("lookup_ip")`라고 치기만 해도 실제 실행할 수 있는 함수를 쏙 꺼내올 수 있게 됨

---

## 라우터 (Router)

레지스트리를 만들었다면, 이름으로 함수를 꺼내와 **실행**해주는 라우터 함수를 만들어야 함. 이 라우터 안에서 핵심은 딕셔너리의 `.get()` 메서드와 안전망 처리.

1. **안전하게 함수 꺼내기 (`.get()`)**
    - 만약 `tool_registry["없는이름"]` 처럼 대괄호로 꺼내려고 하면, 키가 없을 때 프로그램이 에러(`KeyError`)를 내며 완전히 멈춰버립니다.
    - 하지만 `tool_registry.get("없는이름")` 처럼 `.get()`을 쓰면 프로그램이 멈추지 않고 안전하게 `None`을 돌려줍니다.
2. **지어낸 이름 잡아내기**
    - LLM이 환각(Hallucination) 때문에 목록에 없는 엉뚱한 도구 이름을 골라오면 `.get()` 결과가 `None`이 됩니다.
    - 라우터는 `if func:`로 함수가 진짜 존재하는지 확인하고, 없을 때는 무시하고 넘어가는 게 아니라 `[오류] 등록되지 않은 도구`라고 명확하게 사람에게 경고를 남깁니다.
3. **꺼낸 함수 실행하기**
    - 꺼내온 함수(`func`)에 LLM이 넘겨준 인자(`choice["args"]`)를 괄호 안에 넣어서 실행합니다: `func(choice["args"])`
    - 이 한 줄 덕분에 도구가 100개가 되더라도 `if-elif` 문을 쓰지 않고 단 한 줄로 모든 함수를 실행할 수 있게 됩니다.

---

**6교시 구조의 장점 — 확장성**

이렇게 레지스트리와 라우터 구조(6-4 과제인 `tool_router.py`)를 완성해 두면 엄청난 장점이 생깁니다.

도전 문제 6-7에서 **"새로운 도구(**`count_by_ip`**)를 하나 더 추가하라"**고 했을 때, 5교시 방식이었다면 라우터 코드(조건문 내부)를 직접 뜯어고쳐야 했을 것입니다.

하지만 6교시 구조에서는 **라우터 함수(`route_tool_call`)는 단 한 글자도 건드리지 않고**, 오직 `tool_registry["count_by_ip"] = count_by_ip` 처럼 레지스트리 딕셔너리에 함수를 등록만 해주면 시스템이 알아서 새 도구를 인식하고 실행합니다. 이것이 현대적인 프로그램 개발에서 말하는 **'유지보수가 좋은 코드'**의 핵심 원리입니다.

| **하려는 일** | **쓰는 코드** |
| --- | --- |
| 도구를 등록한다 | `tool_registry["lookup_ip"] = lookup_ip` (괄호 없이) |
| 이름으로 함수를 꺼낸다 | `func = tool_registry.get(name)` |
| 꺼낸 함수를 실행한다 | `func(choice["args"])` |
| 없는 이름을 알린다 | `print("[오류] 등록되지 않은 도구:", name)` |
| 한 줄로 실행한다 | `route_tool_call(choice)` |

#### `.get()` — 없는 키는 `None`

```python
registry = {"count_failed_logins":1}
print(registry.get("count_failed_logins"), registry.get("block_everything"))
# 1 None
```

| **쓰는 것** | **키가 없을 때** |
| --- | --- |
| `registry[name]` | `KeyError` 로 멈춘다 |
| `registry.get(name)` | `None` — `if func:` 로 확인할 수 있다 |

⚠ LLM 이 목록에 없는 도구 이름을 보낼 수 있습니다. 그래서 `[]` 가 아니라 `.get()` 으로 꺼냅니다.

# 7교시: 승인 게이트

- 왜 승인 게이트(Approval Gate)가 필요한가?
    - 조회/카운팅 같은 안전한 도구는 시스템에 해를 끼치지 않음.
    - 계정 잠금이나 IP 차단 같은 변경/차단 도구는 되돌리기 어려움. LLM이 오판하거나 해커에 속으면 문제 발생
        
        → 판단은 LLM이 하되, 시스템에 변화를 주는 위험한 행동ㅇ르 하기 전에 무조건 사람의 확인을 받
        

## 게이트(Gate)의 작동 논리

> 원칙 — 승인 조건은 완벽하게 깐깐해야 한다!
> 
- 화이트리스트 방식: 시스템은 어떤 도구가 윟머한지 미리 리스트로 알고 있어야 함. 이는 LLM에 물어보지 않고 파이썬 코드로 고정해두기.
- 거절 중심 설계: 답변 확인할 때 지정된 형식과 대답만 정확하게 일치할 때만 통과되도록 하기. 나머지는 다~ 거절

## 왜 '보류(held)'된 것도 기록으로 남겨야 하는가?

- 보안 에이전트가 어떤 목표를 받았고, 어떤 행동을 취했는지 `agent_result.json` 이라는 감사 로그(Audit Log)에 저장
- 실행된 것만 기록하면 안 되는 이유
    - 해커가 공격 시도해서 LLM이 계정을 잠그려고 했는데 담당자가 바빠서 거절하거나 무시했다고 가정.
    - 실행 안되었더라고 “해커 공격→LLM 잠금시도→사람 보류”라는 전체 맥락이 기록에 남아야 나중에 보안 담당자가 추적 가능.
    - 그래서 실행 결과에는 성공한 값뿐만 아니라 보류 되었더는 뜻의 “held”도 기록 데이터로 남겨둬야 함.
